# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The Kuronyx Sciences (veterinary compounding pharmacy) website and back office, served as static/dynamic PHP/HTML/JS from `public_html/` — no build step, no package manager, no framework. `public_html/` is deployed as-is to Hostinger shared hosting. Beyond the marketing pages, the site also runs a DB-backed public intake system (GS-441524 prescription requests, veterinary account applications) and a staff admin panel — see "GS-441524 platform" below.

## Architecture

### Marketing site
- `public_html/index.html` — a long single-page HTML document (hero, "what we are", "why this matters", credentials, dispatches/newsletter, enquiry form) with inline `<style>` and inline `<script>` for scroll-reveal and the section rail. No templating; edit sections directly.
- `public_html/about/`, `for-veterinarians/`, `pet-parents/` (landing page), `for-cat-owners/` (the prescription form itself), `journal/`, `request-received/` — routed pages (each a directory with `index.php`), sharing chrome via `includes/layout-header.php` / `layout-footer.php`. A page sets `$pageTitle`, `$pageDescription`, `$canonical`, `$robotsNoindex`, `$activeNav`, `$wideWrap`, `$backHref`/`$backLabel` before including the header.
- `public_html/js/subscribe.js` — standalone handler for the newsletter subscribe form (`#subscribeForm`) on `/dispatches`.
- `public_html/Privacy Policy.html` — the policy text, a standalone static page. **Its public address is `/privacy-policy/`** (a Karandeep review comment: a clean URL for the footer link): `public_html/privacy-policy/index.php` serves this SAME file (not a copy) and adds only a `<base href="/">` (the policy's own links are relative, e.g. Back to site) and a canonical tag on the way out. The FILE IS NEVER EDITED for this, because `privacy_policy_version()` is a fingerprint of its bytes (an edit would start a new consent version). The old `/Privacy%20Policy.html` is redirected (301) to `/privacy-policy/` by one `.htaccess` rule (`^Privacy\ Policy\.html$`, escaped space); the file stays in place so, if that rule were ever not applied, the old address keeps working instead of dying (a static file cannot have a PHP fallback like the other moved pages). The footer on every page, Home, both consent checkboxes, the enquiry form's privacy note and the sitemap all use `/privacy-policy/`. Tests: `00b_site_restructure.php` (the page is the file plus the two tags, links everywhere, file untouched, `.htaccess` rule). After deploy: `curl.exe -sI https://kuronyx.in/Privacy%20Policy.html` must be a 301 to `/privacy-policy/`, and resubmit the sitemap.

### Legacy Brevo endpoints (`public_html/php/`)
Called via `fetch()` from the front end. Predate the GS-441524 platform — these were part of the original single-page site, not this project's work.
  - `config.php` — thin shim; requires `../includes/db-config.php` for the actual Brevo constants (see "Secrets" below). Kept only so `send-welcome.php`/`send-enquiry.php`'s `require_once 'config.php'` still works.
  - `send-welcome.php` — called by `subscribe.js` on newsletter signup; sends a Brevo welcome email, then adds the contact to the Brevo list only if the email send succeeded.
  - `send-enquiry.php` — called by the inline enquiry-form script on the Home page (`#enquiry`, the only Write to us form; there is no contact page any more); validates fields server-side and sends the enquiry to `RECEIVER_EMAIL` via a Brevo template.
  - `unsubscribe.php` — GET-based landing page (linked from emails) that removes an email from Brevo list 7. No ownership proof on the `?email=` param — anyone can unsubscribe any address; not yet fixed (low severity, tracked but not urgent).
  - `webhook.php` — Brevo webhook receiver; requires a `?secret=` query param matching `BREVO_WEBHOOK_SECRET` (added 2026-09-13 — see "Known issue" below) before doing anything else. On a `delivered` event, upserts the contact into the Brevo list. Logs every request to `webhook.log` under `private_storage_path()` (off-webroot — moved there the same day, see below), with `FILE_APPEND | LOCK_EX` so two webhook deliveries arriving at once (Brevo can send events in parallel) can't interleave their writes mid-line and corrupt a log entry.
- **Privacy note on the Write to us form** (a Karandeep review comment, written against the old contact page; the form now lives on Home): `index.html` has `<p class="privacy-note">We'll use this only to reply to you. See our <a href="./Privacy%20Policy.html">Privacy Policy</a>.</p>` between the Message box and the button (vets type patient and owner details into the box). Karandeep's wording was used as asked; a possible extra line telling vets not to put personal details there was offered and not taken. The newsletter form has no such note (email only). Test: `00b_site_restructure.php` (text, link, position before the button, mutation-checked).
- `send-welcome.php`/`send-enquiry.php` share a CORS pattern: allow `https://kuronyx.in`, `https://www.kuronyx.in`, and localhost/127.0.0.1 for the `Access-Control-Allow-Origin` response header, AND now also reject (403) processing entirely when the Origin isn't recognized — the allow-list used to only control whether a browser could *read* the response, not whether the server acted on the request, which meant a `mode:'no-cors'` + `text/plain` fetch from any site could silently trigger a real send. Both also rate-limit by IP via `rate_limited()` (`includes/auth.php`, backed by the `rate_limit_hits` table) — 5 requests/hour. `rate_limited()` wraps its count-then-insert in the same serialized DB transaction as the login lockout's `reserve_login_attempt()` (see above) — a plain check-then-insert as two separate autocommit statements, even "insert first, check second", lets concurrent requests interleave between them and all pass the count check before any of their inserts actually commit. Keep this pattern consistent if you touch either file.
- `public_html/php/.htaccess` denies direct access to `.log`/`.env`/`.ini`/`.bak`/`.sql` files in that folder — defense in depth on top of no longer writing anything there.
- The forms no longer POST to Netlify (removed 2026-10-02): the site is hosted on Hostinger, where a POST to `/` does nothing, so the old "backup mirror" never stored anything. Submissions go only to the PHP endpoints. The hidden `bot-field` input is now a real honeypot — `send-welcome.php`/`send-enquiry.php` silently succeed without sending when it's filled. Both endpoints also cap field lengths, drop `replyTo` (the submitter's address is only in the template params, so a plain "Reply" can't write to an unverified address), only accept `kuronyx.in`/`www.kuronyx.in`/`SITE_URL` origins (`allowed_site_origin()` in `auth.php` — no localhost in production; set `SITE_URL` for local dev), and verify Cloudflare Turnstile when `TURNSTILE_*` keys are set: `js/captcha.js` asks `php/captcha-config.php` for the public site key, renders the widget in any `form[data-captcha]`, and forms send the token as `cf-turnstile-response` in the JSON body (`captcha_verify($token)`). No keys configured = no widget, no check.
- **The forms never show a raw browser error**: the enquiry form on the homepage and the newsletter form (Home and `/journal/`) post through `KuronyxPost.send()` (`public_html/js/post-json.js`, loaded before them; `subscribe.js` pages need it too) instead of calling `res.json()` themselves. That used to throw when the server answered with anything that is not JSON (a PHP error page, the site's own HTML error page when the database is down, a 500, a host-level 413 or rate-limit page) and the catch printed the parser's message (`Unexpected token '<', "<!doctype"... is not valid JSON`) as the form status; a dropped connection printed `Failed to fetch`. `send()` never throws and answers `{ ok, data, message }`: the endpoint's own JSON `message` when it sent one ("Too many requests. Please try again later."), "Something went wrong on our side. Please try again, or email hello@kuronyx.in." for anything that is not usable JSON, "We couldn't reach the server. Check your connection and try again, or email hello@kuronyx.in." for a network failure, and a 5xx JSON message gets the "try again, or email" appended. The fallback address is `hello@kuronyx.in` (the one the contact page already shows; `orders@` is only an internal sending address). Only HTTP 2xx with `success: true` counts as success. Tests: `tests/cases/85b_post_json_helper.php` runs the helper under Node with a stub `fetch` (`tests/lib/post_json_test.js`; skipped if Node is not installed) and checks the pages statically. Any new form that posts to a `/php/` endpoint should use it.
- **A Turnstile token works once, so the forms reset the widget after every answer**: `send-enquiry.php` / `send-welcome.php` verify the token BEFORE they check the fields and call Brevo (the 429 rate limit and the Origin check come earlier, so those do NOT spend it), so a refused submission (400 field error, mailer 500) used to leave the form holding a used token and the retry was refused with "Please complete the verification check" until the page was reloaded. The contact page, the homepage enquiry form and `subscribe.js` call `KuronyxCaptcha.reset(form)` right after `KuronyxPost.send(...)` returns, whatever the answer (a success matters too: the newsletter's "Subscribe another" reuses the form). Nothing may `throw`/`return` between the send and the reset. **If Cloudflare's script cannot load, the form says so instead of failing for ever** (a Karandeep review comment): `js/captcha.js` used to set `enabled = true` as soon as the config said Turnstile was on, BEFORE the script had loaded, so with the script blocked (an ad blocker or privacy extension, a clinic network, a flaky connection) no widget appeared, `token()` returned '' and the visitor met "Please complete the verification check" for a check they could not see, on every try (the server refuses a form with no token). Now `enabled` is true only once the script has loaded AND the widget is drawn; a script error, no answer within 10 s, a script that loads without a real `window.turnstile` (a blocker's stand-in), or a widget `error-callback` shows "Verification couldn't load. Please email hello@kuronyx.in directly." under every `form[data-captcha]` (above the button; hello@, the visitor-facing address the other form errors use, not the internal ops@ inbox); a later success (`callback`, or the script arriving after the wait) clears it. `KuronyxCaptcha.blocked` is '' when all is well, the message above on failure, or "Verification is still loading. Please try again in a moment." while loading; BOTH submit handlers (the Home enquiry form and `subscribe.js`) check it after their own field checks and BEFORE sending, so a doomed request does not spend the 5/hour limit. Not configured (no keys) = nothing changes. Tests: `tests/lib/captcha_test.js` (12 scenarios under Node against a pretend page and a stub Turnstile) run by `tests/cases/85d_captcha_unavailable.php` (also checks both handlers stop before `KuronyxPost.send`); 9 mutations caught; checked once in a real browser. Server side is unchanged: with keys set it still refuses a missing token, and `captcha_verify()` still fails OPEN only if Cloudflare is unreachable FROM THE SERVER.
The enquiry forms also check the phone in the browser with the server's own rule (`/^[0-9+()\-\s.]{5,30}$/`, so "+91 98xxx ext 5" is caught before the token is spent) and say what is wrong ("Phone number: use digits only (spaces and + ( ) - . are fine)"); change the rule in all three places together. **The browser first turns every kind of space into a plain one** (`phoneField.value.replace(/\s+/g, ' ').trim()`, in place, before checking and sending): JavaScript's `\s` matches non-breaking spaces (what WhatsApp, contact cards and websites paste) but PHP's `\s` without `/u` is ASCII-only, so a number the browser accepted could still get the server's 400 after the token was spent (found in a review of this check; a text-only comparison of the two regexes could not see it). The message says WHY: invalid characters ("use digits only"), "looks too short" (<5) or "too long" (>30). Known and left alone: the rule (also the server's) accepts a "number" with no digits at all (`.....`, `+++++`) - requiring a minimum number of digits would need the server regex and the tests changed together; and when several fields are wrong the generic message is shown (the phone field is still highlighted). Tests: `tests/cases/85c_captcha_reset_and_phone.php` (static order check, the browser rule equals the server's text, the rule's behaviour under Node, and the server's 400 for that phone).
- **No marketing tick on the cat-owner form** (removed 2026-10-24, a Karandeep review comment): "I'd also like to receive occasional updates" only wrote a `marketing` row into `consent_records` - nothing read it and nothing added the email to the Brevo list, so people were promised updates that never came, and erasing a case deleted that consent row anyway. The newsletter has its own sign-up (`/journal/`, the homepage) with a welcome email and unsubscribe. If cat owners should ever be subscribed from this form: call the same signup as `send-welcome.php`, and keep the proof of consent in its OWN table (email, time, IP, policy version, source) that a case erasure does not delete - `consent_records` belongs to the case. Newsletter (Brevo) data is still not covered by erasure.
- `/for-cat-owners` and `/for-veterinarians/apply` (the DB-backed intake forms, not the legacy endpoints above) are also rate-limited (8 submissions/hour/IP), but via `rate_limit_reserve()`/`rate_limit_release()` (`auth.php`): the hit is reserved atomically up front and handed back when the submission is bounced for ordinary field errors, so correcting a typo (or several people behind one NAT address) doesn't burn the budget; upload/captcha/token failures still count. `/for-veterinarians/apply` requires a registration certificate upload; staff must follow `docs/vet-approval-checklist.md` (state council lookup, phone callback) before approving.

### GS-441524 platform (DB-backed intake + admin)
- **Data**: `db/schema.sql` is the canonical MySQL schema (run once against the Hostinger DB); `db/schema.sqlite.sql` is a hand-maintained SQLite mirror used by local dev and the test suite (no build step generates it — update both when the schema changes). `db/migrations/` holds incremental ALTERs for already-provisioned databases.
- **Shared includes** (`public_html/includes/`, each self-guards against direct HTTP access):
  - `db.php` — `db(): PDO`, driver toggle via `DB_DRIVER` (`mysql` in prod, `sqlite` for local dev/tests). Also installs a site-wide exception handler that never leaks stack traces to visitors.
  - `db-config.php` — **gitignored**, created manually per environment. Copy `db-config.sample.php`. Holds DB credentials, `PRIVATE_STORAGE_PATH`, `SETUP_TOKEN`, and all Brevo settings (`BREVO_API_KEY`, template IDs, sender/receiver, `BREVO_VERIFIED_SENDERS`, `EMAIL_DRY_RUN`) — this is the single source of secrets for the whole app, including the legacy `php/config.php` shim.
  - `auth.php` — **three separate session cookies** (`GS_SESSION_NAMES`): `kuronyx_staff_sid` for everything under `/admin/`, `kuronyx_vet_sid` for the vet portal pages (login/activate/forgot/reset/`portal/`), `kuronyx_sid` for everything else (public forms). `gs_session_area()` picks one from the script path; `current_staff()`/`current_vet()` only start their own session if its cookie is present (so a visitor never gets one they don't have), and `download.php` — the one page serving both — switches between them and passes the staff actor id to `audit()` explicitly. **A page that renders a form and has no `require_login()`/`require_*` must call `csrf_token()` before any output** (the login pages do), or the cookie can't be sent. `gs_session_cleanup()` (`session-cleanup.php`, 1-in-100 requests) deletes stale `sess_*` files itself, since PHP's own GC is often off for a custom `save_path`. `csrf_token()`/`csrf_field()`/`csrf_verify()`, `current_staff()`/`require_login()`/`require_role([...])`, login lockout (8 attempts/15min via `login_attempts`), `audit($action, $entityType, $entityId, $metadata, $actorType)`. Both login pages call `reserve_login_attempt()`, which atomically checks the lockout count and reserves this attempt as a failure in one DB transaction (`begin_serialized_window_transaction()` — `BEGIN IMMEDIATE` on SQLite, since that engine only allows one writer for the whole database at a time once a write transaction is open; `SELECT ... FOR UPDATE` on MySQL/InnoDB, selecting the actual matching row ids — not `SELECT COUNT(*)` — since an aggregate locking read isn't reliably documented to take the same next-key/gap locks over the scanned range as a row-returning one, so the count is taken in PHP over the locked rows instead of trusting SQL to lock an aggregate), returning `null` if already locked out and otherwise a row id the caller passes to `mark_login_attempt_succeeded()` once `password_verify()` (run *after* reserving, since it's the slow, bcrypt-based step) confirms success. A plain check-then-insert as two separate statements — even "insert first, check second" — isn't enough on its own: without the transaction+locking-read wrapper, concurrent requests can still interleave between the two statements and all pass the count check before any of their inserts commit. `rate_limited()` (below) uses the same atomic pattern. `require_login()`/`require_vet_login()` (and `download.php`'s own inline equivalent, since it can't call either without wrongly redirecting the other identity) re-check both the account's active/status flag **and** `password_fingerprint_matches()` on every request (for staff this is `staff_identity_now()` in `auth.php`, shared by `require_login()` and `download.php`; it also re-reads the staff member's CURRENT **role, name and email** from `staff_users` and `require_login()` refreshes the session copy with them, so a role changed in the database - a demotion by hand today, a role-change screen one day - applies on the very next request instead of when that person next signs in; the session only expires after 4h of INACTIVITY, so before this someone who kept working kept the old role indefinitely; same query as before, no extra cost; `tests/cases/67b_staff_identity_refresh.php`) — the latter compares a `sha256(password_hash)` fingerprint stored in the session at login against the current DB value, so a password reset invalidates every other live session immediately (including one an attacker had stolen) without needing a schema-level session-revocation counter, since `password_hash()`'s random salt already guarantees the fingerprint changes on every password change. `require_vet_login()` (and `download.php`'s inline equivalent) also re-check the linked `vet_applications.status` is still `'approved'`, not just the account's own status — the admin review actions below update both tables inside one transaction, but this independent check means portal/document access doesn't depend on that sync always holding (a future action that forgets to touch the account, a restored backup, etc.), the same "don't depend on every status-changing action remembering" philosophy `activate.php` already uses.
  - `mailer.php` — `verified_senders()` (the `BREVO_VERIFIED_SENDERS` allow-list, falling back to the single `SENDER_EMAIL`), `send_transactional_email()` (raw Brevo send with an optional `$fromEmail`/`$fromName` override that must be a verified sender, respects `EMAIL_DRY_RUN`) and `send_case_email()` (sends + always logs to `case_emails`, including the `sender` used, even on failure). Nothing in the app sends an email on its own — every send is a staff-initiated `send_email` action from an admin compose form.
  - **An email with no answer is "unknown", not "failed"** (a Karandeep review comment): a slow Brevo reply past the 15 s limit or a dropped connection used to be recorded as "failed" - but Brevo may have accepted the message, so staff clicked Send again and the owner got it twice. `mail_send_outcome()` (`includes/mail-outcome.php`, dependency-free so it is unit-tested) classifies a call: **sent** (HTTP 201), **not sent** (Brevo answered 4xx/5xx = refused, or the request never left: no connection / TLS handshake, `CURLINFO_APPCONNECT_TIME` = 0; a 10 s connect timeout was added so that case is clean) and **unknown** (no answer after the handshake, or an odd 2xx/3xx). `MailException` carries `->outcome` (`not_sent` default, `unknown` via `MailException::unknown()`). `send_case_email()` now returns `'sent'|'failed'|'unknown'` (it used to return bool) and marks the `case_emails` row `unknown` (VARCHAR column: no migration). The case page shows `mail_unconfirmed_text()` ("We couldn't confirm whether this email was sent - it may have gone out. Before sending it again, check Brevo's transactional email logs (search for <address>) or ask them."), keeps the draft, audits `email_unconfirmed`, and the history shows a neutral "Unconfirmed" badge with a "May have been sent" line. The veterinary-application page writes "NOT CONFIRMED" to its notes, same message, audit `email_unconfirmed`; the staff invitation says it may have gone out and audits `staff_invite_unconfirmed`. A 5xx from Brevo is still "not sent" (they refused it) - a product decision; flip it in `mail_send_outcome()` if a doubled email is ever judged better than a missed one. The deferred reset emails are unchanged (nobody sees an outcome; a duplicate reset is harmless). Test harness: `EMAIL_DRY_RUN_UNKNOWN_TO` (like `_FAIL_TO`, never set in a real db-config.php). Tests: `70b_email_unconfirmed.php` (the classification as a pure function, the three pages, a refused send unchanged; 8 mutations caught).
  - **No email addresses in the server's error log** (a Karandeep review comment): the PHP error log sits OUTSIDE the data-erasure process, so an address written there outlives the erasure of the case it belongs to. Log lines name the case and the log row instead (`[mailer] case email #45 (GS-123) failed: ...`, `(VA-7)` for applications), and anything we do not control - an exception message, or Brevo's reply, which can echo the address ("email address 'x@y' is invalid") - goes through `log_safe()` (`includes/log-safe.php`, loaded by `db.php`: replaces anything that looks like an address with `[email]` and cuts to 500 characters). EVERY `error_log()` line carrying `->getMessage()` or a `$response` must use it (mailer, vet application page, staff invitation, both forgot-password pages, the uncaught-exception handler in `db.php`, data-erasure, orphan sweep, the legacy `send-enquiry` / `send-welcome` / `webhook`); a new log line must not name `$recipient` / `$email` / form data. `tests/cases/70c_log_safe.php` fails if one does (a scan of every `error_log(` line in `public_html/`), tests the helper, and reads the REAL server log after real failed and unconfirmed sends (the harness's simulated errors echo the address like Brevo can). **How long Hostinger keeps the PHP error log is not documented** (checked 2026-11-02): to find out, look at the oldest line and the size of the `.logs/error_log_<domain>` file in File Manager, or ask Hostinger support; PHP error logging is OFF by default there (hPanel > Advanced > PHP Configuration > logErrors), so nothing is logged until it is switched on.
  - **The email composer no longer wipes what staff typed** (a Karandeep review comment): `js/admin-email-compose.js` (shared by the case page and the veterinary application page) used to overwrite the Subject and Message the moment another template was picked - no warning, no way back, and "Blank" cleared the message. It now remembers the text of the last template it applied (starting from the server's template for the selected option, so a KEPT DRAFT after a failed or unconfirmed send counts as edited too). Untouched boxes swap at once as before; edited boxes are left alone, the dropdown goes back, and an inline bar (`#email-template-notice`, `alert-warn`, `role=status`) asks "You have edited this message. Replace it with the '<name>' template? Your edits will be lost." with **Replace** / **Keep mine**. After a Replace an **Undo** button puts the previous subject, message and template back, and the first keystroke after a Replace removes the Undo offer so it can never overwrite newer typing. Inline on purpose, NOT `confirm()`: a browser can switch those dialogs off, which would leave the dropdown dead (the same reason the data-erasure page uses a `<dialog>`); the bar's buttons are `type=button` (they sit inside the send form). Line endings (`
` from a textarea) do not count as edits. Tests: `tests/lib/email_compose_test.js` (15 scenarios against a pretend DOM under Node) run by `tests/cases/70d_email_compose.php` (skipped without Node; also fails if the script uses `confirm(`); 6 mutations caught; checked once in a real browser.
  - Password reset helpers in `auth.php` — `issue_password_reset()` / `find_password_reset_account()` / `complete_password_reset()` (whitelisted to `staff_users` and `vet_accounts`; only a SHA-256 hash of the one-time token is stored, 60-minute expiry — 7 days for a new staff member's invitation, which reuses this machinery, see `staff/` below — cleared on use) and `site_url()` (emailed links are built from `SITE_URL`/`https://kuronyx.in`, never the request's Host header, to prevent reset-link poisoning). Pages: `admin/forgot-password.php` + `admin/reset-password.php` (staff and admins share `staff_users`) and `for-veterinarians/forgot-password.php` + `reset-password.php` (only `status='active'` vet accounts — pending ones still use their activation link, suspended ones stay locked out). **The vet confirmation tells everyone where to find their activation link** (a Karandeep review comment): a vet who lost the approval email naturally tries "Forgot your password", gets nothing (pending accounts get no reset by design: activation is the staff-issued link, and `activate.php` re-checks the application is approved) and waits for an email that never comes. The confirmation now adds "Haven't activated your account yet? Use the link from your approval email, or write to ops@kuronyx.in for a new one." It is part of the message shown for every address, so it reveals nothing about who has an account; the address is ops@ like the rest of the vet pages. Letting this page email a fresh activation link to pending accounts was considered and NOT done (it would automate an email staff send by hand, and keep the response identical for every address). Test in `96_password_reset.php` (pending account gets no email; the message is identical for a pending, unknown and active address; mutation-checked). This is the one place the app emails automatically without a staff member composing the message, because the requester is the account holder (the other is the invitation an admin triggers by creating a staff account); it's capped at 3 emails/address/hour and 15 requests/IP/hour, and the response is identical whether or not an account exists.
  - `upload.php` / `storage-path.php` — `store_uploaded_file()` validates PDF/JPG/PNG up to 10MB and stores off-webroot under `PRIVATE_STORAGE_PATH`; never web-accessible directly.
  - **The storage fallback is refused on a live host** (a Karandeep review comment; the user chose "warn plus refuse"): `private_storage_path()` used to fall back SILENTLY to `private_storage_fallback` when `PRIVATE_STORAGE_PATH` was missing or empty - on the live server too. After a config rewrite or a deploy that dropped the setting, new prescriptions would have gone into a second folder, split from the old ones: downloads look in whichever folder is configured at that moment (documents "disappear" for staff), erasure only deletes from the configured one, and the second folder may not be in the backups. Now the fallback works only for LOCAL requests (`gs_config_is_local_request()`: localhost, 127.0.0.1, ::1, *.localhost, or no server name = command line), quietly, as before - local dev and the tests are unaffected (they set their own path or run on a local host). On any other host it throws `StorageNotConfiguredException` and writes ONE `[storage] PRIVATE_STORAGE_PATH is not set on a live host ... REFUSED` line to the error log per request; `db.php`'s exception handler answers it with a plain 503 "Temporarily unavailable. Uploads and documents cannot be used right now..." (instead of the generic 500). It covers every user of the function: the intake forms' uploads, document downloads, erasure, the orphan sweep (its exceptions are already caught and logged) and the webhook log (Brevo retries on the non-2xx). The cost: during such a misconfiguration the upload forms show the 503 page (the one-time token and an hourly-limit slot are spent), and a local copy opened through a non-local host name (a LAN name, a tunnel) with no path set is refused too - set `PRIVATE_STORAGE_PATH`. The config loader is deliberately different (it only warns, the user chose not to refuse there: a missing config would take the whole site down, a missing storage path only stops uploads). `dirname(__DIR__, 2)` is the folder above `public_html` only because `includes/` sits directly inside it (commented in `storage-path.php` and the session-folder code in `auth.php`). Tests: `tests/cases/99e_storage_path_refusal.php` (runs the real files in a throwaway tree in a separate PHP process on live and local host names; 5 mutations caught).

If the send fails the account still exists and the admin is told to have the person use "Forgot your password?" (which works for any active account) — the admin is **never shown the link or a password**, because anyone holding the link could set the password themselves, which is exactly what this design avoids. The active/inactive toggle is a single `UPDATE staff_users SET active = 1 - active WHERE id = ?` rather than a read-then-write — flips whatever the row's value actually is at that moment, so a double-click or two admins acting on the same row can't silently cancel each other out via a stale read.

## Conventions added by the 2026-10 security/concurrency review (keep following these)

- **Atomicity**: anything that must not race uses either a single conditional statement (`UPDATE ... WHERE token/lock_version = ?` + `rowCount()`), a UNIQUE/PRIMARY KEY violation caught with `is_unique_violation($e, 'table', 'column')` (`auth.php`) — **never** a bare `getCode() === '23000'`: that SQLSTATE is the generic code for *every* integrity error (duplicate key, foreign key, NOT NULL), so it retried a dispatch slug 5× on a foreign-key error and could tell staff an unrelated failure was "a duplicate"; the helper reads each engine's own wording (SQLite: code 19 + `UNIQUE constraint failed: t.col`; MariaDB/MySQL: 1062 + `for key 'col'`; pass `true` for a PRIMARY KEY, which MySQL always names `PRIMARY`) and `tests/cases/62_unique_violation.php` fails on a bare check; or `run_serialized_transaction()` (`auth.php`: `BEGIN IMMEDIATE` on SQLite / `FOR UPDATE` on MySQL, auto-retried on deadlock). Never "SELECT then INSERT/UPDATE" as separate autocommit statements. `audit()` goes *inside* the transaction, before `commit()`.
- **`rowCount()` differs by engine**: SQLite counts the rows an UPDATE *matched*, MySQL/MariaDB (production) only the rows it *changed* (no `FOUND_ROWS` flag is set). So read `rowCount() === 0` as "my WHERE condition no longer matched" only when the UPDATE always changes something (a `lock_version + 1`, a status change, clearing a token); an UPDATE that can set a column to the value it already has looks like a lost race on MariaDB while passing on SQLite. Found 2026-10-18 by the MariaDB run ("request more information" on an application already under review), which is why status actions that would not change the status are refused instead. Never use SQL `||` for string concatenation in test setup either: it is OR on MariaDB.
- **Optimistic locking**: `gs_requests.lock_version` (update_final / assign_staff / change_status) and `dispatches.lock_version` — hidden `expected_lock_version` field, every write does `lock_version = lock_version + 1`. Don't use `updated_at` for this (1-second resolution).
- **Folder pages are published with a trailing slash** (`/about/`, `/for-veterinarians/`, `/pet-parents/`, `/for-cat-owners/`, `/journal/`, `/for-veterinarians/apply/`, `/request-received/`): each is a folder with an `index.php`, and Hostinger's LiteSpeed 301s the slash-less form to the slashed one (checked live 2026-10-05 on `/assets`, `/php`, `/js`). Canonicals, `sitemap.xml`, the nav (`layout-header.php`, `index.html`), internal links and `header('Location: …')` targets must use the slash form so nothing publishes a URL that redirects; `tests/cases/00_public_pages.php` fails if one doesn't (the built-in test server doesn't redirect, so only a static check can see it). We deliberately did **not** use `DirectorySlash Off`. `.htaccess` also 301s `www.kuronyx.in` to `https://kuronyx.in` (it was serving a second copy of the site with 200), as the first rule so `http://www…` is one hop. After deploy, check `curl -sI https://kuronyx.in/about/` (200), `…/about` (301 to the slash) and `curl -sI https://www.kuronyx.in/` (301 to `https://kuronyx.in/`) — the `.htaccess` has never run on the live server before this deploy, and it sets its own `Content-Security-Policy` header, which could replace the host's `upgrade-insecure-requests` one, so confirm both CSP values are present.
- **Paged lists need a unique tiebreaker**: `created_at` has 1-second resolution, so a burst of rows shares a timestamp and MySQL may return ties in any order per query — `LIMIT/OFFSET` then repeats or skips rows between pages. Every paged list orders by its date column then `id DESC` (audit log, GS requests, vet applications, admin dispatches — the dispatch list used to stop silently at 200 rows, so older dispatches became impossible to find and edit; it now pages Newer/Older like the others). All of them read the page from `list_page()` (`auth.php`), which caps it at 100,000: an absurd `?page=` used to overflow `(page-1)*size` into a float in the SQL and 500; `audit_log` has an explicit `(created_at, id)` index (`idx_audit_created_id`). Keep the `id` tiebreaker on any new paged list.
- **List filters are whitelisted** (`list_filter()` / `list_ignored_filters_notice()` in `auth.php`; GS requests: status/source/formulation, vet applications: status): a value not in the allowed list is ignored and a "Filter ignored" note says which one, instead of being passed to the query where a typo (`?status=aproved`) matched nothing and showed "No requests match these filters" with the dropdown reading "All". Not a security issue (always a bound parameter) — a misleading-page fix. Add any new dropdown filter the same way, with its allowed values coming from the shared lists below.
- **Status lists live in ONE place**: `includes/case-statuses.php` defines `GS_CASE_STATUSES` (every case status, workflow order), the named subsets `GS_TERMINAL_STATUSES` (finished with: erasable, retention clock) and `GS_FULFILMENT_STATUSES` (a vet may see formulation/price/tracking), and `VET_APPLICATION_STATUSES`. The case list, case page, erasure code (`ERASABLE_CASE_STATUSES`), vet portal and application list all build off them — never retype a list. The two SQL schema files can't, so `tests/cases/65_case_statuses.php` fails if the constants differ from the `status` ENUM in `db/schema.sql` / the CHECK in `db/schema.sqlite.sql` (same order), if a subset leaves the full list, if any other PHP file retypes the list, or if an email template on the case page is keyed by a non-status. **To add a status**: add it to `GS_CASE_STATUSES` (and a subset if it belongs to one), write the migration + both schema files, add it to `STATUS_TONES` in the same file (`good` = teal, `bad` = red, `neutral` = plain — a test fails until every status has a tone, so a new status can't silently stay grey), and the tests tell you what else you missed. The badge CSS is **generated** from `STATUS_TONES` by `status_pill_css()` (called in `layout-header.php`), not hand-written; labels come from `status_label()` ("under_review" → "Under Review" — the application list used to show "Under_review"; never hand-roll `ucwords(...)` on a status). Current tones: good = approved, dispatched, finished, published; bad = closed, cancelled, rejected, suspended; everything else neutral. `approved`/`rejected` also colour the Active/Deactivated badge (staff page) and the sent/failed badge (email log) — keep that in mind before changing them.
- **A form that sets `$errors['field']` must PRINT it**: `includes/form-errors.php` has three tiny helpers — `field_class($errors,'x')` (label class, adds `has-error`), `field_error_attrs($errors,'x')` (`aria-invalid` + `aria-describedby` on the input) and `field_error_html($errors,'x')` (the escaped `<span class="field-error" id="err-x">` message). The new-staff form, both password-reset pages, `activate.php`, `tools/setup.php` and the dispatch editor used to set messages like "Use at least 12 characters" / "An account with this email already exists" and only colour the label, so the admin saw a red box and had to guess (the forms are `novalidate`, so the browser's own hints are off too). Use the helpers on any form where the user must be told what is wrong. **The public intake forms (`/for-cat-owners`, `/for-veterinarians/apply`, the portal request form) use the same helpers** - they used to show only the red border plus the banner (a Karandeep review comment: a worried cat owner needs the message more than staff do). Each field prints its message ("Enter a valid phone number", "A prescription upload is required"); a field over its column size says how long it may be (`too_long_message()`: "Too long - 150 characters at most"; a byte-limit hit on the notes says "please shorten it"); `field_class($errors, 'consent', 'checkbox-field')` takes a base class for radio rows and checkbox rows; `form_error_focus_script($errors)` (echo it after the form) moves the cursor to the first field with a message and scrolls to it. A refused UPLOAD is explained under the file that failed (`$uploadField`), with the generic banner above; it still counts against the hourly allowance (`_form` stays set), while ordinary field typos do not. After a failed submit the consent tick is kept (it is not in `$fields`), and `reattach_files_note($errors, 'prescription', ...)` (`form-errors.php`, styled `.reattach-note`: amber edge, normal text colour, bold "Please attach your files again.") sits just above the file field whenever the form came back with an error that is not the file's own - browsers cannot refill file inputs, so the first version, a grey `.field-hint` line, was nearly invisible on the dark page. It is at the upload rather than in the red box at the top because on a long form the box is a screen or more away from the files. **Upload limits**: Hostinger's PHP allows `post_max_size` = `upload_max_filesize` = 1024M and `max_file_uploads` = 20 (read off a temporary page on 2026-10-24, since deleted), so the host never refuses our files - the 10 MB per file limit (`MAX_UPLOAD_BYTES`) is enforced only by our own code AFTER the whole file has arrived, and `db.php`'s plain-text "too large (limit X)" page for a body over `post_max_size` is effectively unreachable in production (3 files x 10 MB; it can still happen on a host with a low limit, and the local `php.ini` sets 12M). What helps people is knowing the limit BEFORE a slow upload: the forms print it from the one constant (`upload_size_text(upload_limit_bytes())`: "up to 10 MB" - see the next bullet for why it is not the bare constant) and every file input carries `data-max-bytes`, which `js/upload-limit.js` checks the moment a file is chosen - a too-big file is cleared and "That file is 23.4 MB - the limit is 10 MB per file..." is printed under the field (`KuronyxUploadLimit.tooBigMessage()`); the server still re-checks and now says the size and the limit too ("That file is empty" is its own message). Tests: `tests/cases/80c_upload_limits.php`. A new file input on a public form needs `data-max-bytes="<?= upload_limit_bytes() ?>"` and the script tag; the test scans for it. **"Was a file chosen?" is answered by `upload_was_chosen($field)` (`upload.php`), never by `empty($_FILES[x]['name'])`**: PHP's `empty()` is true for the string "0", so a file literally named `0` was reported as a missing prescription / certificate, and an optional document with that name was silently dropped (the case or application was saved without it). The helper looks at the upload ERROR code (`UPLOAD_ERR_NO_FILE` = nothing chosen); a crafted array-valued field counts as chosen so `store_uploaded_file()` refuses it as "Invalid upload.". Tests: `tests/cases/80e_file_named_zero.php` (also fails if `empty()` on a file name comes back). Other fixes made at the same time: the vet application's "Website" field had a message but no highlight at all, its "Verification documents (optional)" heading contradicted the required certificate (now "Verification documents", with the required/optional split in the hint), the duplicate `fc()` helpers were deleted in favour of `field_class()`, and the refill helper that existed three times (`ov()` in the cat-owner and portal forms, `old_val()` in the vet application) is now ONE `old_value($old, 'field')` in `form-errors.php` (escaped value, empty when there is none); `66_field_errors.php` fails if any page under `public_html/` defines its own `ov()` / `old_val()` / `fc()` again. Tests: `tests/cases/80b_public_form_messages.php` (cat owners + vet application; the portal form's case sits in `80_vet_portal.php` because that file later suspends the account) and `66_field_errors.php`, which now also scans these three pages, including the fields whose key is only known at run time (the `$required` list and every `field_class()` label must print their message). `tests/cases/66_field_errors.php` fails if one of the listed pages sets a field message it never prints; page tests use `assert_field_error()` / `assert_no_field_error()` (`tests/lib/assert.php`), which check the element, because a bare `assert_contains('has-error', …)` is satisfied by the stylesheet on every page — that is how this went unnoticed. **Never write a PHP closing tag (or the short echo tag) inside a `//` comment**: it ends PHP mode and the rest of the comment is printed into every page that includes the file.
- **Audit rows record who did it**: `audit()` copies the actor's name into `audit_log.actor_name` when it writes the row (`audit_actor_name()` in `auth.php`) — staff from `staff_users`, vets from their `vet_applications.full_name` — so the log still reads right after a rename/removal. It's a real column, not `metadata_json`, because `erase_gs_request()` nulls `metadata_json` on case entries. **Never store a name for `'public'` actors**: that's an anonymous visitor (for the intake forms, the pet owner/applicant), whose name is exactly the data erasure must be able to clear. The log page shows `actor_name`, else the current name via join (rows from before the column existed have none), else `Staff #12`/`Vet #5`. A staff member finishing a password reset is logged as `staff` with their id (like the vet reset), not `public`. Migration `2026-10-05_add_audit_actor_name.sql` must be run **before** deploying — every audited action's INSERT names the column.
- **Double-submit**: `one_time_field($key)` / `consume_one_time_token($key)` (`auth.php`) on forms with irreversible side effects (send email, public intake forms). Up to `OTT_MAX_PER_KEY` (8) live tokens are kept per key so the same form open in two tabs / re-shown by Back still works; each is single-use. Tests read it with `extract_ott()`.
- **MySQL limits SQLite can't enforce**: `TEXT` columns are 65,535 *bytes* (use `text_byte_errors()` alongside the character cap), `patient_weight_kg` is `DECIMAL(5,2)` (use `parse_patient_weight()`, max 999.99). Mail failures are logged with `error_log('[mailer] ...')` including Brevo's response.
- **Login**: per-IP cap (`LOGIN_IP_MAX_ATTEMPTS`) + per-email lockout, one identical error message for every failure, dummy `password_verify()` on unknown accounts, failures audited only for real accounts. Forgot-password defers the Brevo call until after the response (`fastcgi_finish_request()` on PHP-FPM).
- **Admin staff toggle** sends an explicit `set_active` (never a flip) and refuses to deactivate the last active admin.
- **Inputs**: array-valued `$_GET`/`$_POST` are rejected centrally in `db.php`; oversized POST bodies get a real error there too; use `field_length_errors()` against column sizes; passwords max 72 bytes (`PASSWORD_MAX_BYTES`).
- **Outbound email**: `unresolved_placeholder()` blocks sending template markers like `[insert payment link]`; every curl call needs `CURLOPT_TIMEOUT`.
- **The config loader warns about a stale copy** (a Karandeep review comment): `includes/config-loader.php` finds `db-config.php` one level above `public_html` first and falls back to `includes/db-config.php` (local dev and the tests rely on the fallback, so it is NEVER refused). The dangerous state is invisible: the real file moved above `public_html` and a stale copy (real passwords, maybe old ones) left inside the web folder, ignored by the loop so everything looks fine. `gs_config_path()` now writes to the error log, once per request and paths only (never contents): a loud `[config] SECURITY` line when BOTH files exist (always, even on a developer's machine; the safe one is still used), and a quieter one when only the in-folder copy is used on a request that is not local (`gs_config_is_local_request()`: localhost, 127.0.0.1, ::1, *.localhost, or no server name = command line). After moving the file, delete `includes/db-config.php` ON THE SERVER, not just from the repo. Test: `tests/cases/99d_config_loader_warnings.php` (runs a copy of the loader in a throwaway folder tree, in a separate PHP process, with its error log pointed at a file; 7 mutations caught).
- `client_ip()` replaces raw `REMOTE_ADDR` (opt-in `TRUST_PROXY_IP_HEADER`, see `db-config.sample.php`). **Keep `TRUST_PROXY_IP_HEADER` OFF in production.** Tested 2026-10-02 on Hostinger with a temporary page: a laptop on wifi and a phone on mobile data each showed their own real, different `REMOTE_ADDR`, and no `X-Forwarded-For`/`X-Real-IP`/`CF-Connecting-IP` headers were set — so there is no proxy in front and `REMOTE_ADDR` is already the real visitor IP. Enabling it would only let attackers spoof their IP and bypass every per-IP limit. Re-test only if hosting/CDN changes. The per-IP login cap (`login_ip:` buckets) calls `rate_limited(..., false)` so blocked attempts aren't recorded and a flood can't extend its own block. Sessions live in `SESSION_SAVE_PATH` (fallback `session_fallback/`, gitignored) with a 4h idle lifetime.

PHP's session handling already sends `no-store, no-cache, must-revalidate` when a session starts (`session.cache_limiter` defaults to `nocache`), but that is a host setting we cannot see and nothing in the code said it mattered, so it is explicit; our values differ from PHP's on purpose so a test can tell them apart. **Set them AFTER the session has started** - `session_start()` sends PHP's cache headers itself and replaces anything set before it (the first version did exactly that and a test caught it). Test: the last test in `67c_private_page_headers.php` (5 mutations caught). **The STAFF logout (`admin/logout.php`) keeps the silent redirect on purpose**: the user judged it a rare stale-tab case (the token lives the whole session, staff sessions end after 4 h idle, the open page makes a failure noticeable) and chose the vet portal as the stronger case (vets are the people most likely on shared clinic computers, with patient data on screen). Revisit if a second person ever shares an admin machine. Tests: `tests/cases/67c_private_page_headers.php` (ten admin pages; the vet dashboard, the new-request page AND the case page `portal/view.php` - the one with the owner's and patient's names, added 2026-11-02 after a Karandeep review comment made us check coverage - plus the portal's "case not found" answer, both logouts and the signed-out redirect). Not verified on the live host (the admin is not deployed yet): after deploy, check the headers with `curl.exe -s -D - -o NUL https://kuronyx.in/admin/login.php | Select-String "cache-control|pragma|expires"` and that Back after logout shows the sign-in page.

Test in `80_vet_portal.php` (used, made-up and missing token; mutation-checked). The staff `admin/reset-password.php` message is unchanged.

## Local development

## Testing

`tests/` is a zero-dependency PHP integration test suite (no Composer is installed, and none is needed elsewhere in the project). Run it with:
```
php tests/run.php
```
It self-bootstraps the right PHP extensions, starts a throwaway `php -S` instance against `public_html/` backed by a disposable SQLite DB (`db/schema.sqlite.sql`), drives it with curl (sessions, CSRF, multipart uploads), and tears everything down — including restoring your real `db-config.php` exactly as it was. `EMAIL_DRY_RUN` is set for the test run so no real Brevo API calls happen. Add new cases under `tests/cases/` (numbered files, each returning a closure that takes the shared `TestEnv $env`).

The suite runs on SQLite by default, but **production is MySQL/MariaDB**, so also run it against a throwaway MySQL before shipping anything that touches transactions, locking, rate limiting or schema: set `KURONYX_TEST_MYSQL="host=127.0.0.1;port=3306;user=root;pass=..."` (the user needs CREATE/DROP DATABASE) and run `php tests/run.php` — it creates a `kuronyx_test_*` database from `db/schema.sql` and drops it afterwards. `tests/cases/94_real_concurrency.php` then races 24 separate PHP processes (own connections) through `reserve_login_attempt()`/`rate_limited()` to prove the `SELECT … FOR UPDATE` windows hold and don't deadlock past the retry cap (`run_serialized_transaction()`, 6 attempts). Verified 2026-10-02 on MariaDB 11.8.9 (production's version): gap-lock deadlocks (error 1213) genuinely occur — with no retry the login/rate-limit helpers fail under 24 concurrent processes, and the old cap of 3 failed the mixed-keys case at 48+; cap 6 passes at 96. Don't lower it; it also runs on SQLite with `KURONYX_TEST_CONCURRENCY=1`. `tests/cases/01_schema_parity.php` (always runs) fails if `db/schema.sql` and `db/schema.sqlite.sql` drift apart (tables, columns, NOT NULL, UNIQUE, enum values, indexes, foreign keys) or if a migration adds something `schema.sql` lacks. SQLite-only tests skip themselves under MySQL (`skip_test()`). **On the owner's Windows machine** a portable MariaDB 11.8.9 (production's version) is installed at `C:\Users\Vasu\mariadb-11.8.9-winx64\` — not a service, outside the repo; run `start-mariadb-for-kuronyx-tests.cmd` there (127.0.0.1:3307 only), then `$env:KURONYX_TEST_MYSQL = "host=127.0.0.1;port=3307;user=root;pass=" + (Get-Content C:\Users\Vasu\mariadb-11.8.9-winx64\kuronyx-test-root-password.txt)` and `php tests/run.php`; its `README-kuronyx.txt` has stop/remove steps. Verified 2026-10-08: the full suite (188 tests) passes on MariaDB 11.8.9 as well as SQLite (the remaining skips are the SQLite-only trigger/`BEGIN IMMEDIATE` simulations). Run it there before every deploy that touches queries, schema or error handling.

## Abuse protection (added 2026-10-02)

- **Login lockout is keyed on account + IP** (`login_identifier()` in `auth.php`, stored as `email|ip` in `login_attempts.identifier`), not the email alone — otherwise anyone could lock the real admin out by failing 8 logins from anywhere. `clear_login_attempts($base)` (used by both reset-password pages) clears every IP's rows for an account via `SUBSTR` (not `LIKE`). Distributed guessing at one account is bounded by the 12-char minimum password and the per-IP `login_ip:` cap.
- **Anonymous upload forms** (`/for-cat-owners`, `/for-veterinarians/apply`) have no site-wide daily upload cap (removed 2026-10-02 — it let a bot flood block every real submission). Bot/flood defence is Cloudflare Turnstile (`TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY`, set in production; no-op when unset; **fails open if Cloudflare is unreachable**) on the two upload forms, the newsletter and enquiry forms, plus the per-IP limit (8 submissions/hour) and one-time tokens. Disk use is unbounded apart from those — watch the storage folder.

## Review fixes (2026-10-02, round 2)

- `php/webhook.php` only upserts to the newsletter list when the `delivered` payload's `template_id` equals `BREVO_TEMPLATE_ID` (the welcome email). `delivered` fires for every transactional send (case emails, activation, resets), whose recipients never opted in. If Brevo ever omits `template_id` for the welcome email, signups still work (`send-welcome.php` adds the contact itself).
- `client_ip()` with `TRUST_PROXY_IP_HEADER` uses the RIGHT-most `X-Forwarded-For` entry (the one our proxy appended; the left-most is client-controlled), validated as an IP, else `REMOTE_ADDR`. Assumes exactly one trusted proxy.
- `run_serialized_transaction()` begins inside the `try` (so SQLite's BEGIN IMMEDIATE "database is locked" is retried) and its ROLLBACK can't throw over the original error.
- Login (staff + vet): non-`FILTER_VALIDATE_EMAIL` input skips the DB lookup and shares one `(invalid-email)` lockout bucket (MySQL's accent-insensitive collation would otherwise match `admín@…` to the real row with a fresh bucket each); inactive/not-activated accounts run the dummy `password_verify()` so they don't time differently.
- `send_case_email()`: once the email has gone out, a failure to update its log row is only logged (never a 500 that invites a duplicate send); any `Throwable` during the send marks the row `failed`.
- `store_uploaded_file()` PDF check (`pdf_active_content_verdict()` in `upload.php`) also decodes `#xx` name escapes, inflates `/ObjStm` object streams (32MB cap) and refuses encrypted PDFs. Still a heuristic, not a virus scan.
