# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The Kuronyx Sciences (veterinary compounding pharmacy) website and back office, served as static/dynamic PHP/HTML/JS from `public_html/` — no build step, no package manager, no framework. `public_html/` is deployed as-is to Hostinger shared hosting. Beyond the marketing pages, the site also runs a DB-backed public intake system (GS-441524 prescription requests, veterinary account applications) and a staff admin panel — see "GS-441524 platform" below.

## Architecture

### Marketing site
- `public_html/index.html` — a long single-page HTML document (hero, "what we are", "why this matters", credentials, dispatches/newsletter, enquiry form) with inline `<style>` and inline `<script>` for scroll-reveal and the section rail. No templating; edit sections directly.
- `public_html/about/`, `for-veterinarians/`, `for-cat-owners/`, `contact-us/`, `dispatches/`, `request-received/` — routed pages (each a directory with `index.php`), sharing chrome via `includes/layout-header.php` / `layout-footer.php`. A page sets `$pageTitle`, `$pageDescription`, `$canonical`, `$robotsNoindex`, `$activeNav`, `$wideWrap`, `$backHref`/`$backLabel` before including the header.
- `public_html/js/subscribe.js` — standalone handler for the newsletter subscribe form (`#subscribeForm`) on `/dispatches`.
- `public_html/Privacy Policy.html` — standalone static page, not linked into the SPA's section rail.

### Legacy Brevo endpoints (`public_html/php/`)
Called via `fetch()` from the front end. Predate the GS-441524 platform — these were part of the original single-page site, not this project's work.
  - `config.php` — thin shim; requires `../includes/db-config.php` for the actual Brevo constants (see "Secrets" below). Kept only so `send-welcome.php`/`send-enquiry.php`'s `require_once 'config.php'` still works.
  - `send-welcome.php` — called by `subscribe.js` on newsletter signup; sends a Brevo welcome email, then adds the contact to the Brevo list only if the email send succeeded.
  - `send-enquiry.php` — called by the inline enquiry-form script on `/contact-us`; validates fields server-side and sends the enquiry to `RECEIVER_EMAIL` via a Brevo template.
  - `unsubscribe.php` — GET-based landing page (linked from emails) that removes an email from Brevo list 7. No ownership proof on the `?email=` param — anyone can unsubscribe any address; not yet fixed (low severity, tracked but not urgent).
  - `webhook.php` — Brevo webhook receiver; requires a `?secret=` query param matching `BREVO_WEBHOOK_SECRET` (added 2026-09-13 — see "Known issue" below) before doing anything else. On a `delivered` event, upserts the contact into the Brevo list. Logs every request to `webhook.log` under `private_storage_path()` (off-webroot — moved there the same day, see below), with `FILE_APPEND | LOCK_EX` so two webhook deliveries arriving at once (Brevo can send events in parallel) can't interleave their writes mid-line and corrupt a log entry.
- `send-welcome.php`/`send-enquiry.php` share a CORS pattern: allow `https://kuronyx.in`, `https://www.kuronyx.in`, and localhost/127.0.0.1 for the `Access-Control-Allow-Origin` response header, AND now also reject (403) processing entirely when the Origin isn't recognized — the allow-list used to only control whether a browser could *read* the response, not whether the server acted on the request, which meant a `mode:'no-cors'` + `text/plain` fetch from any site could silently trigger a real send. Both also rate-limit by IP via `rate_limited()` (`includes/auth.php`, backed by the `rate_limit_hits` table) — 5 requests/hour. `rate_limited()` wraps its count-then-insert in the same serialized DB transaction as the login lockout's `reserve_login_attempt()` (see above) — a plain check-then-insert as two separate autocommit statements, even "insert first, check second", lets concurrent requests interleave between them and all pass the count check before any of their inserts actually commit. Keep this pattern consistent if you touch either file.
- `public_html/php/.htaccess` denies direct access to `.log`/`.env`/`.ini`/`.bak`/`.sql` files in that folder — defense in depth on top of no longer writing anything there.
- The forms no longer POST to Netlify (removed 2026-10-02): the site is hosted on Hostinger, where a POST to `/` does nothing, so the old "backup mirror" never stored anything. Submissions go only to the PHP endpoints. The hidden `bot-field` input is now a real honeypot — `send-welcome.php`/`send-enquiry.php` silently succeed without sending when it's filled. Both endpoints also cap field lengths, drop `replyTo` (the submitter's address is only in the template params, so a plain "Reply" can't write to an unverified address), only accept `kuronyx.in`/`www.kuronyx.in`/`SITE_URL` origins (`allowed_site_origin()` in `auth.php` — no localhost in production; set `SITE_URL` for local dev), and verify Cloudflare Turnstile when `TURNSTILE_*` keys are set: `js/captcha.js` asks `php/captcha-config.php` for the public site key, renders the widget in any `form[data-captcha]`, and forms send the token as `cf-turnstile-response` in the JSON body (`captcha_verify($token)`). No keys configured = no widget, no check.
- `/for-cat-owners` and `/for-veterinarians/apply` (the DB-backed intake forms, not the legacy endpoints above) are also rate-limited (8 submissions/hour/IP), but via `rate_limit_reserve()`/`rate_limit_release()` (`auth.php`): the hit is reserved atomically up front and handed back when the submission is bounced for ordinary field errors, so correcting a typo (or several people behind one NAT address) doesn't burn the budget; upload/captcha/token failures still count. `/for-veterinarians/apply` requires a registration certificate upload; staff must follow `docs/vet-approval-checklist.md` (state council lookup, phone callback) before approving.

### GS-441524 platform (DB-backed intake + admin)
- **Data**: `db/schema.sql` is the canonical MySQL schema (run once against the Hostinger DB); `db/schema.sqlite.sql` is a hand-maintained SQLite mirror used by local dev and the test suite (no build step generates it — update both when the schema changes). `db/migrations/` holds incremental ALTERs for already-provisioned databases.
- **Shared includes** (`public_html/includes/`, each self-guards against direct HTTP access):
  - `db.php` — `db(): PDO`, driver toggle via `DB_DRIVER` (`mysql` in prod, `sqlite` for local dev/tests). Also installs a site-wide exception handler that never leaks stack traces to visitors.
  - `db-config.php` — **gitignored**, created manually per environment. Copy `db-config.sample.php`. Holds DB credentials, `PRIVATE_STORAGE_PATH`, `SETUP_TOKEN`, and all Brevo settings (`BREVO_API_KEY`, template IDs, sender/receiver, `BREVO_VERIFIED_SENDERS`, `EMAIL_DRY_RUN`) — this is the single source of secrets for the whole app, including the legacy `php/config.php` shim.
  - `auth.php` — **three separate session cookies** (`GS_SESSION_NAMES`): `kuronyx_staff_sid` for everything under `/admin/`, `kuronyx_vet_sid` for the vet portal pages (login/activate/forgot/reset/`portal/`), `kuronyx_sid` for everything else (public forms). `gs_session_area()` picks one from the script path; `current_staff()`/`current_vet()` only start their own session if its cookie is present (so a visitor never gets one they don't have), and `download.php` — the one page serving both — switches between them and passes the staff actor id to `audit()` explicitly. **A page that renders a form and has no `require_login()`/`require_*` must call `csrf_token()` before any output** (the login pages do), or the cookie can't be sent. `gs_session_cleanup()` (`session-cleanup.php`, 1-in-100 requests) deletes stale `sess_*` files itself, since PHP's own GC is often off for a custom `save_path`. `csrf_token()`/`csrf_field()`/`csrf_verify()`, `current_staff()`/`require_login()`/`require_role([...])`, login lockout (8 attempts/15min via `login_attempts`), `audit($action, $entityType, $entityId, $metadata, $actorType)`. Both login pages call `reserve_login_attempt()`, which atomically checks the lockout count and reserves this attempt as a failure in one DB transaction (`begin_serialized_window_transaction()` — `BEGIN IMMEDIATE` on SQLite, since that engine only allows one writer for the whole database at a time once a write transaction is open; `SELECT ... FOR UPDATE` on MySQL/InnoDB, selecting the actual matching row ids — not `SELECT COUNT(*)` — since an aggregate locking read isn't reliably documented to take the same next-key/gap locks over the scanned range as a row-returning one, so the count is taken in PHP over the locked rows instead of trusting SQL to lock an aggregate), returning `null` if already locked out and otherwise a row id the caller passes to `mark_login_attempt_succeeded()` once `password_verify()` (run *after* reserving, since it's the slow, bcrypt-based step) confirms success. A plain check-then-insert as two separate statements — even "insert first, check second" — isn't enough on its own: without the transaction+locking-read wrapper, concurrent requests can still interleave between the two statements and all pass the count check before any of their inserts commit. `rate_limited()` (below) uses the same atomic pattern. `require_login()`/`require_vet_login()` (and `download.php`'s own inline equivalent, since it can't call either without wrongly redirecting the other identity) re-check both the account's active/status flag **and** `password_fingerprint_matches()` on every request — the latter compares a `sha256(password_hash)` fingerprint stored in the session at login against the current DB value, so a password reset invalidates every other live session immediately (including one an attacker had stolen) without needing a schema-level session-revocation counter, since `password_hash()`'s random salt already guarantees the fingerprint changes on every password change. `require_vet_login()` (and `download.php`'s inline equivalent) also re-check the linked `vet_applications.status` is still `'approved'`, not just the account's own status — the admin review actions below update both tables inside one transaction, but this independent check means portal/document access doesn't depend on that sync always holding (a future action that forgets to touch the account, a restored backup, etc.), the same "don't depend on every status-changing action remembering" philosophy `activate.php` already uses.
  - `mailer.php` — `verified_senders()` (the `BREVO_VERIFIED_SENDERS` allow-list, falling back to the single `SENDER_EMAIL`), `send_transactional_email()` (raw Brevo send with an optional `$fromEmail`/`$fromName` override that must be a verified sender, respects `EMAIL_DRY_RUN`) and `send_case_email()` (sends + always logs to `case_emails`, including the `sender` used, even on failure). Nothing in the app sends an email on its own — every send is a staff-initiated `send_email` action from an admin compose form.
  - Password reset helpers in `auth.php` — `issue_password_reset()` / `find_password_reset_account()` / `complete_password_reset()` (whitelisted to `staff_users` and `vet_accounts`; only a SHA-256 hash of the one-time token is stored, 60-minute expiry, cleared on use) and `site_url()` (emailed links are built from `SITE_URL`/`https://kuronyx.in`, never the request's Host header, to prevent reset-link poisoning). Pages: `admin/forgot-password.php` + `admin/reset-password.php` (staff and admins share `staff_users`) and `for-veterinarians/forgot-password.php` + `reset-password.php` (only `status='active'` vet accounts — pending ones still use their activation link, suspended ones stay locked out). This is the one place the app emails automatically, because the requester is the account holder; it's capped at 3 emails/address/hour and 15 requests/IP/hour, and the response is identical whether or not an account exists.
  - `upload.php` / `storage-path.php` — `store_uploaded_file()` validates PDF/JPG/PNG up to 10MB and stores off-webroot under `PRIVATE_STORAGE_PATH`; never web-accessible directly.
  - `layout-header.php` / `layout-footer.php` — shared chrome for every routed page above and every admin page.
- **Public intake**: `/for-veterinarians/apply` (→ `vet_applications` + `vet_application_documents`), `/for-cat-owners` (→ `gs_requests` + `gs_request_documents`, prescription upload required). Both redirect to `/request-received` on success and show a generic "check the highlighted fields" banner on validation failure (no per-field message text is rendered — only the `has-error` CSS class).
- **Staff admin** (`public_html/admin/`, session + CSRF + `require_role`):
  - `login.php` / `logout.php`, plus `setup.php` — **not in `public_html/`**: its source is `tools/setup.php`, deliberately never deployed; upload it by hand to `public_html/admin/` only to create the first admin, then delete it and `SETUP_TOKEN` from the server (`public_html/admin/setup.php` is gitignored; the test harness copies it in for a run). One-time, token-gated first-admin creation via `SETUP_TOKEN`; the actual creation is guarded by claiming the single fixed-`PRIMARY KEY` row in `setup_lock` — a plain "is `staff_users` empty?" check, even as one SQL statement, isn't safe under MySQL's default non-locking reads, where two concurrent requests can both observe an empty table).
  - `gs-requests/` — list/filter, per-case status changes (+ history, no email side effect; **any status can move to any other, deliberately — no transition rules or required-field checks, e.g. a case can go to `dispatched` without a tracking number; staff are trusted and the small team prefers flexibility. Don't add guards unless asked**), internal notes, final formulation/fulfilment fields, staff assignment, and a "Send an email" panel: a template dropdown (`$emailTemplates` in `view.php`, one per owner-facing status, rebuilt each render from the case's current final-formulation/price/courier fields), a sender dropdown restricted to `verified_senders()`, and a recipient dropdown restricted to this case's own `owner_email`/`vet_email` (never an arbitrary address — enforced server-side too, not just by the dropdown). Staff edit the template (formulation, price, payment link, etc.) before hitting Send; a "No Email Needed" button records that choice (`email_not_needed` audit entry) without sending anything. Nothing is ever sent automatically. Sent/failed messages are logged to `case_emails` (now including `sender`) regardless of outcome. `update_final` and `assign_staff` are optimistically locked on `gs_requests.lock_version` (a hidden `expected_lock_version` field on each form, set from the value the page was loaded with) — a blind `UPDATE` would let two staff editing the same case's formulation or assignment at once silently overwrite each other with no warning. Every write to the row (including `change_status`) increments `lock_version` by exactly 1; a mismatch means the row changed since the form was loaded, so the submission is rejected with a "reload and try again" message instead of applied. A plain `updated_at` comparison was tried first but isn't safe for this — `DATETIME` here only has second-level precision, so two edits within the same second would carry an identical "expected" value and the conflict wouldn't actually be caught.
  - `veterinary-applications/` — list/filter, approve/reject/request-info/suspend (append-only `internal_notes` log, no email side effect). Approving provisions a `vet_accounts` row (see below) but does not email it; a "Generate Activation Link" button (re)creates the token on demand and shows the raw URL for that render only (the raw token is never persisted, so it can only appear right after being generated) so it can be reviewed and sent via the same template/sender/recipient "Send an email" panel as gs-requests, or explicitly marked "No Email Needed." Both suspending and rejecting an application also suspend its linked `vet_accounts` row (rejecting didn't used to — an approved-then-rejected application left the vet's portal login and any pending activation link still working) — `activate.php` independently also requires the linked application to still be `'approved'` at the moment of activation, not just when its own token-issuing page first loaded, so this doesn't depend on every status-changing action remembering to update the account. `approve`/`reject`/`suspend` each wrap their `vet_applications` status update and the matching `vet_accounts` update/insert in one DB transaction, so the two can't commit independently and land out of sync under concurrent review actions — `require_vet_login()` also independently re-checks the application is still approved on every portal request as a second layer (see `auth.php` above), so this doesn't become the only thing standing between the two tables drifting. `approve`'s account-creation `INSERT` also catches a `23000` (UNIQUE) violation on `vet_accounts.vet_application_id` gracefully — two staff approving the same application at once can both pass the in-transaction read and race to insert, and the DB constraint (not the earlier read) is what actually prevents a duplicate account. Re-approving a previously suspended/rejected application reconciles the existing `vet_accounts` row instead of leaving it stuck suspended: an already-activated account (has a `password_hash`) goes straight back to `active`, keeping its existing password; a never-activated one is reset to `pending_activation` with a fresh token, since any earlier one is long cleared. `send_email` also re-checks any `/for-veterinarians/activate.php?token=...` link embedded in the message body against the account's *current* `activation_token_hash` before actually sending — "Generate Activation Link" always invalidates the previous token, so a message drafted before a regeneration (by the same staff member in another tab, or someone else) could otherwise go out with a dead link unnoticed.
  - `dispatches/` — CMS for the public `/dispatches` blog (draft/publish, slug auto-generation). Publishing/saving inserts or updates directly and only disambiguates the slug (appending a random suffix) on an actual `23000` (UNIQUE) violation from the database, retried up to 5 times — rather than checking for a conflicting slug first and only suffixing if one is found, which would let two staff saving around the same auto-generated slug both pass the check before either commits.
  - `audit-log/` — admin-only (`require_role(['admin'])`), paginated.
  - `data-erasure/` — admin-only DPDP tooling (`includes/data-protection.php`). `erase_gs_request()` permanently deletes one case's uploaded files, consent records (IP/UA), logged emails and internal notes, blanks the owner/patient/vet fields to `[erased]`/NULL, clears status-history notes and the metadata of that case's audit entries, and stamps `gs_requests.erased_at` — keeping the case id, status history, formulation/price and audit rows (without metadata). Only `finished`/`closed`/`cancelled`/`rejected` cases are erasable; requires typing `ERASE`; files are deleted only after the DB transaction commits; an erased case can't be emailed. The page also lists terminal cases untouched for `RETENTION_MONTHS` (db-config.php, default 36 — a placeholder: **confirm the legally required prescription/dispensing record retention with the pharmacist/legal before relying on it**) for manual review — nothing is deleted automatically. Covers GS-441524 cases only, not `vet_applications`/newsletter (Brevo) data. Consent records store `privacy_policy_version()` — a fingerprint (`pp-` + first 16 hex of sha256) of `Privacy Policy.html`, so any edit to the policy automatically produces a new version.
  - `staff/` — admin-only; list/create staff accounts and toggle `active` (deactivating is re-checked by `require_login()` on every request, so it takes effect immediately, not on next login; an admin can't deactivate their own account). Creating a staff account inserts directly and catches a `23000` (UNIQUE) violation on `email` rather than checking for an existing row first, same reasoning as the dispatch slug above. The active/inactive toggle is a single `UPDATE staff_users SET active = 1 - active WHERE id = ?` rather than a read-then-write — flips whatever the row's value actually is at that moment, so a double-click or two admins acting on the same row can't silently cancel each other out via a stale read.
  - `download.php` (site root) — the only way documents are ever served; staff can access any document, a signed-in vet only documents on their own `gs_requests` (never `vet_application` documents); authenticated + audited (`document_accessed`).
- **Veterinarian portal** (`public_html/for-veterinarians/`) — a separate session identity (`current_vet()`/`require_vet_login()` in `auth.php`) with its own session cookie (`kuronyx_vet_sid`), fully independent of the staff one — being signed in as both in one browser is fine and signing out of one doesn't affect the other (no more manual "clear the other identity" at login). `login.php`, `activate.php` (token-based password set-up after approval, 7-day expiry, hashed token), `portal/index.php` (dashboard of the vet's own `gs_requests`), `portal/new-request.php` (submits directly with `source='veterinarian'` and `vet_account_id` set — a signed prescription upload is required per request, same as the cat-owner form, stored as a `gs_request_documents` row with `doc_type='prescription'`), `portal/view.php` (read-only case view, no internal notes/staff fields), `portal/logout.php`.

## Conventions added by the 2026-10 security/concurrency review (keep following these)

- **Atomicity**: anything that must not race uses either a single conditional statement (`UPDATE ... WHERE token/lock_version = ?` + `rowCount()`), a UNIQUE/PRIMARY KEY violation caught as SQLSTATE `23000`, or `run_serialized_transaction()` (`auth.php`: `BEGIN IMMEDIATE` on SQLite / `FOR UPDATE` on MySQL, auto-retried on deadlock). Never "SELECT then INSERT/UPDATE" as separate autocommit statements. `audit()` goes *inside* the transaction, before `commit()`.
- **Optimistic locking**: `gs_requests.lock_version` (update_final / assign_staff / change_status) and `dispatches.lock_version` — hidden `expected_lock_version` field, every write does `lock_version = lock_version + 1`. Don't use `updated_at` for this (1-second resolution).
- **Double-submit**: `one_time_field($key)` / `consume_one_time_token($key)` (`auth.php`) on forms with irreversible side effects (send email, public intake forms). Up to `OTT_MAX_PER_KEY` (8) live tokens are kept per key so the same form open in two tabs / re-shown by Back still works; each is single-use. Tests read it with `extract_ott()`.
- **MySQL limits SQLite can't enforce**: `TEXT` columns are 65,535 *bytes* (use `text_byte_errors()` alongside the character cap), `patient_weight_kg` is `DECIMAL(5,2)` (use `parse_patient_weight()`, max 999.99). Mail failures are logged with `error_log('[mailer] ...')` including Brevo's response.
- **Login**: per-IP cap (`LOGIN_IP_MAX_ATTEMPTS`) + per-email lockout, one identical error message for every failure, dummy `password_verify()` on unknown accounts, failures audited only for real accounts. Forgot-password defers the Brevo call until after the response (`fastcgi_finish_request()` on PHP-FPM).
- **Admin staff toggle** sends an explicit `set_active` (never a flip) and refuses to deactivate the last active admin.
- **Inputs**: array-valued `$_GET`/`$_POST` are rejected centrally in `db.php`; oversized POST bodies get a real error there too; use `field_length_errors()` against column sizes; passwords max 72 bytes (`PASSWORD_MAX_BYTES`).
- **Outbound email**: `unresolved_placeholder()` blocks sending template markers like `[insert payment link]`; every curl call needs `CURLOPT_TIMEOUT`.
- `client_ip()` replaces raw `REMOTE_ADDR` (opt-in `TRUST_PROXY_IP_HEADER`, see `db-config.sample.php`). **Keep `TRUST_PROXY_IP_HEADER` OFF in production.** Tested 2026-10-02 on Hostinger with a temporary page: a laptop on wifi and a phone on mobile data each showed their own real, different `REMOTE_ADDR`, and no `X-Forwarded-For`/`X-Real-IP`/`CF-Connecting-IP` headers were set — so there is no proxy in front and `REMOTE_ADDR` is already the real visitor IP. Enabling it would only let attackers spoof their IP and bypass every per-IP limit. Re-test only if hosting/CDN changes. The per-IP login cap (`login_ip:` buckets) calls `rate_limited(..., false)` so blocked attempts aren't recorded and a flood can't extend its own block. Sessions live in `SESSION_SAVE_PATH` (fallback `session_fallback/`, gitignored) with a 4h idle lifetime.
- `download.php` always sends `Content-Disposition: attachment` (with a `filename*=UTF-8''…` form) plus `Content-Security-Policy: default-src 'none'; sandbox` (uploads are untrusted) and audits denied access. `store_uploaded_file()` also refuses PDFs containing `/JavaScript`, `/JS`, `/Launch`, `/EmbeddedFile(s)` or `/RichMedia` — a cheap heuristic (name obfuscation defeats it), not a virus scan; staff should still open uploads on a machine with up-to-date protection.
- Pages whose URL carries a one-time token (`reset-password.php` ×2, `activate.php`) send `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. An activation link may only be emailed to a vet application's `professional_email`, never the unverified `clinic_email` (enforced in the composer). The forgot-password pages do the same cheap DB write for unknown and real addresses (no bcrypt on only one side). `setup.php` (see `tools/setup.php`) reads the token from `$_GET`/`$_POST` only. Logout is POST + CSRF. `.htaccess` adds HTTPS redirect, X-Frame-Options/frame-ancestors, Referrer-Policy and a short-max-age HSTS (raise it once HTTPS is confirmed solid).
- `unsubscribe.php` confirms on GET and only acts on POST; it still can't prove address ownership (needs a signed link in the Brevo template, or Brevo's built-in unsubscribe).

## Local development

No local dev server or build step is required beyond PHP itself. `local-dev/` (gitignored) holds a machine-specific SQLite DB, off-webroot storage, and a `php.ini` enabling `pdo_sqlite`/`pdo_mysql`/`fileinfo`/`mbstring`. Typical loop:
```
php -c local-dev/php.ini -S localhost:8000 -t public_html
```
`public_html/includes/db-config.php` (gitignored, copy from `db-config.sample.php`) points at the local SQLite file with `DB_DRIVER=sqlite` and carries a local `SETUP_TOKEN`.

## Testing

`tests/` is a zero-dependency PHP integration test suite (no Composer is installed, and none is needed elsewhere in the project). Run it with:
```
php tests/run.php
```
It self-bootstraps the right PHP extensions, starts a throwaway `php -S` instance against `public_html/` backed by a disposable SQLite DB (`db/schema.sqlite.sql`), drives it with curl (sessions, CSRF, multipart uploads), and tears everything down — including restoring your real `db-config.php` exactly as it was. `EMAIL_DRY_RUN` is set for the test run so no real Brevo API calls happen. Add new cases under `tests/cases/` (numbered files, each returning a closure that takes the shared `TestEnv $env`).

The suite runs on SQLite by default, but **production is MySQL/MariaDB**, so also run it against a throwaway MySQL before shipping anything that touches transactions, locking, rate limiting or schema: set `KURONYX_TEST_MYSQL="host=127.0.0.1;port=3306;user=root;pass=..."` (the user needs CREATE/DROP DATABASE) and run `php tests/run.php` — it creates a `kuronyx_test_*` database from `db/schema.sql` and drops it afterwards. `tests/cases/94_real_concurrency.php` then races 24 separate PHP processes (own connections) through `reserve_login_attempt()`/`rate_limited()` to prove the `SELECT … FOR UPDATE` windows hold and don't deadlock past the retry cap (`run_serialized_transaction()`, 6 attempts). Verified 2026-10-02 on MariaDB 11.8.9 (production's version): gap-lock deadlocks (error 1213) genuinely occur — with no retry the login/rate-limit helpers fail under 24 concurrent processes, and the old cap of 3 failed the mixed-keys case at 48+; cap 6 passes at 96. Don't lower it; it also runs on SQLite with `KURONYX_TEST_CONCURRENCY=1`. `tests/cases/01_schema_parity.php` (always runs) fails if `db/schema.sql` and `db/schema.sqlite.sql` drift apart (tables, columns, NOT NULL, UNIQUE, enum values, indexes, foreign keys) or if a migration adds something `schema.sql` lacks. SQLite-only tests skip themselves under MySQL (`skip_test()`).

## Deployment

`.github/workflows/deploy.yml` auto-deploys on every push to `main`: it FTPS-syncs `public_html/` to `/domains/kuronyx.in/public_html/` on Hostinger via `SamKirkland/FTP-Deploy-Action`, using `FTP_SERVER`/`FTP_USERNAME`/`FTP_PASSWORD` repo secrets. There is no CI build/test step — whatever is in `public_html/` on `main` goes live as-is (run `php tests/run.php` yourself before pushing). Note `db/` and `tests/` live outside `public_html/` and are never deployed; DB migrations and `db-config.php` are applied to the server by hand.

## Known issue — rotate the exposed Brevo key

`public_html/php/config.php` used to be tracked in git with a live Brevo API key hardcoded in it. As of 2026-09-12 the key has been moved to `includes/db-config.php` (gitignored) and `config.php` no longer contains any secret — but the key value itself was exposed in git history for some time. **Removing it from the working tree does not erase it from history.** The key should still be rotated in Brevo (Settings → SMTP & API → API Keys) and the new value placed only in each environment's own `db-config.php`. Flag this to the user before assuming it's already been done.

## Known issue — manual production steps required after the 2026-09-13 webhook fix

`public_html/php/webhook.php` had no authentication and logged every request (including real Brevo delivery events — subscriber emails, IPs) to `webhook.log` inside `public_html/php/`, which had no `.htaccess` protection. That log was confirmed publicly downloadable at `https://kuronyx.in/php/webhook.log` before this fix. The code now requires a `?secret=` matching `BREVO_WEBHOOK_SECRET` and logs off-webroot instead — but **two things still need doing by hand on the live server, and neither can be done from this repo**:
1. Delete the existing `public_html/php/webhook.log` from the live server (File Manager/FTP) — deploying the fix does not remove a file that's already there.
2. Update the webhook URL registered in Brevo (Settings → Webhooks) to include `?secret=<value of BREVO_WEBHOOK_SECRET in production's db-config.php>`, and add `BREVO_WEBHOOK_SECRET` to that file if it isn't there yet — otherwise the webhook will start failing with 403s once this code ships. Flag this to the user before assuming either step is already done.

## Abuse protection (added 2026-10-02)

- **Login lockout is keyed on account + IP** (`login_identifier()` in `auth.php`, stored as `email|ip` in `login_attempts.identifier`), not the email alone — otherwise anyone could lock the real admin out by failing 8 logins from anywhere. `clear_login_attempts($base)` (used by both reset-password pages) clears every IP's rows for an account via `SUBSTR` (not `LIKE`). Distributed guessing at one account is bounded by the 12-char minimum password and the per-IP `login_ip:` cap.
- **Anonymous upload forms** (`/for-cat-owners`, `/for-veterinarians/apply`) have no site-wide daily upload cap (removed 2026-10-02 — it let a bot flood block every real submission). Bot/flood defence is Cloudflare Turnstile (`TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY`, set in production; no-op when unset; **fails open if Cloudflare is unreachable**) on the two upload forms, the newsletter and enquiry forms, plus the per-IP limit (8 submissions/hour) and one-time tokens. Disk use is unbounded apart from those — watch the storage folder.

## Review fixes (2026-10-02, round 2)

- `php/webhook.php` only upserts to the newsletter list when the `delivered` payload's `template_id` equals `BREVO_TEMPLATE_ID` (the welcome email). `delivered` fires for every transactional send (case emails, activation, resets), whose recipients never opted in. If Brevo ever omits `template_id` for the welcome email, signups still work (`send-welcome.php` adds the contact itself).
- `client_ip()` with `TRUST_PROXY_IP_HEADER` uses the RIGHT-most `X-Forwarded-For` entry (the one our proxy appended; the left-most is client-controlled), validated as an IP, else `REMOTE_ADDR`. Assumes exactly one trusted proxy.
- `run_serialized_transaction()` begins inside the `try` (so SQLite's BEGIN IMMEDIATE "database is locked" is retried) and its ROLLBACK can't throw over the original error.
- Login (staff + vet): non-`FILTER_VALIDATE_EMAIL` input skips the DB lookup and shares one `(invalid-email)` lockout bucket (MySQL's accent-insensitive collation would otherwise match `admín@…` to the real row with a fresh bucket each); inactive/not-activated accounts run the dummy `password_verify()` so they don't time differently.
- `send_case_email()`: once the email has gone out, a failure to update its log row is only logged (never a 500 that invites a duplicate send); any `Throwable` during the send marks the row `failed`.
- `store_uploaded_file()` PDF check (`pdf_active_content_verdict()` in `upload.php`) also decodes `#xx` name escapes, inflates `/ObjStm` object streams (32MB cap) and refuses encrypted PDFs. Still a heuristic, not a virus scan.
